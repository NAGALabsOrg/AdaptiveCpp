- Interface change (R2): `hipsycl::rt::configure_composition_kernel` in `include/hipSYCL/runtime/composition_adaptivity.hpp` takes three further parameters `group_size_x`, `group_size_y`, `group_size_z` (default 0, meaning none) and sets `known_group_size_x/y/z` when all three are above 0. Reason: a composed kernel launched without a known group size reaches the PTX backend without `.maxntid`, ptxas gives it no register bound, and a 1024-thread launch fails with CU:701 (observed in `collectives/int8` on CUDA). The native group size is structure and does not change between runs of a graph, so it does not change the kernel's identity between runs. `adaptivity_engine.cpp` passes `_block_size`.
- Added case (C32, `naga/sg-tests/device/t_rerun.cpp`): `reruns/a_work_item_kernel_changes_its_range_without_a_new_compilation` (range 64 then 100000, `jit_compile_count` unchanged). Reason: G6 requires that a range given by a launch value never changes kernel identity; work-item kernels are now launched on a fixed 128-wide `nd_range` (`sycl_device_ops.hpp`, `dev/generic_kernel.hpp` `item_kernel`) instead of a range whose automatic group size depends on the count. The same holds for the flag and counter fills.
- Fork change outside the plan's units (cleared by Jack): CBS widening of allocas keeps the original alignment. `src/compiler/cbs/IRUtils.cpp` (`widenedElementType`, `widenedAlignment`, used by `arrayifyAllocas`) and `src/compiler/cbs/SubCfgFormation.cpp` (`arrayifyAllocas`), declared in `include/hipSYCL/compiler/cbs/IRUtils.hpp`. Reason: an alloca such as `[3 x i64]` with `align 16` (24 bytes) was widened into an array of 24-byte elements, so the slices of odd work items were only 8-aligned while the users kept `align 16`; the x86 backend then emitted an aligned `vmovaps` store that faulted (SIGSEGV with `si_code` 128, `rdi` modulo 16 = 8) in the K5 gather on OpenMP (`device_views/a_gather_reads_a_tile_chosen_by_data_after_its_owner_published`). The element size is now padded to a multiple of the original alignment (a byte array) and the widened alloca is aligned to the larger of 64 and the original alignment; nothing else about the arrayification changes. Regression test: `tests/compiler/cbs/overaligned_local_array.cpp` (a 24-byte `alignas(16)` array live across a group barrier, group size 64, run on OpenMP at the default level and with `-O`), run by lit through the `check-cbs` target of the tests build (`lit tests/compiler/cbs`), in the same form as the other tests in that directory.
- C2 changed by decision D18 (Jack; plan file locked, note sg-redesign-decisions is the authority): the graph's memory comes from a per-graph, per-device pool that grows with need instead of an eagerly reserved pool under the 80% limit rule. `graph_options::pool_reservation_bytes` (default 0) only pre-sizes it. A request carries the operations the requesting work already depends on (`pool::allocate(bytes, deps)`; `memory_service::for_producer`, `for_reader` and `acquire_toolchain` take them; the producer passes the writes of its handle, a migration copy the reads of its handle plus the handle's producer, a launch its whole dependency set); a free block is reused only when each of its last users has finished or is in those dependencies, else the pool takes a new slab of the request rounded up to `pool::min_slab_bytes` (4 MiB) and capped at the device's largest single allocation. `placement::wait_for` and `pool_block::wait_for` are removed (a reused block never adds a wait). `errc::pool_exhausted` is replaced by `errc::allocation_refused`; a refused request names the handle and the size. The 80% rule and the old exhaustion errors are gone; `include/hipSYCL/sg/detail/pool_config.hpp` is deleted (still to be removed with `git rm` at the C2 commit). Reason: on the Intel integrated GPU the old default reserved 80% of the 62 GB OpenCL global memory (49.8 GB, pinned system RAM) per graph, which ended in a global OOM kill on 2026-11-23.

Implemented through `graph_services::pool_slabs` and `graph_impl::pool_slab_count()`.
